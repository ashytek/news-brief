## Three features: manual trigger, Vantage recap skip, clustering removed (25 July 2026)
Planned via plan-mode (full plan at the time: `/Users/ashmac/.claude/plans/is-there-a-possibility-lively-starlight.md`), reviewed by an independent second opinion (Fable model) before implementation — the review caught two real bugs in the initial design (a healthcheck false-alarm on the skip path, and a polling query that couldn't actually detect a running pipeline run) that were fixed before writing any code. `npm run build` and `python3 -m py_compile` on every touched pipeline file pass clean after every change; a comprehensive grep sweep confirmed no leftover references to anything removed.

**Feature 1 — Manual pipeline trigger.** A "⚡ Run now" control in the reader header (next to the "Checked Xh ago" status, not the icon row — keeps a costly action off the crowded row with a documented overflow history, and visually distinct from the pre-existing, purely-cosmetic "Refresh feed" icon so the two aren't confused). New route `app/api/pipeline/trigger/route.ts` calls GitHub's `workflow_dispatch` API, gated by: auth, a check against GitHub's own queued/in-progress runs (closes the ~2-4 min blind window between a successful dispatch and the pipeline's own `pipeline_runs` row appearing), a 50-minute staleness escape on a stuck `running` row (workflow times out at 45 min), and a 15-minute cooldown. Two-phase client-side polling (15s while waiting for the run to start, up to 10 min; 30-60s once it's running, up to 45 min) watches `pipeline_runs` for a new row by **id**, not timestamp (avoids clock-skew issues) — refreshes the feed and pipeline-health indicator automatically on completion.

Per Ash's explicit request, a scheduled cron run now skips real work entirely (no Apify/Gemini cost) if a **successful or partial** manual run started within the last 5 hours (`pipeline_runs.trigger_source`, new column, set from `github.event_name` via the workflow YAML) — deliberately excludes failed/still-running manual triggers so a crash can't compound into a ~12h silent gap. The skip path pings the healthcheck as **success** before returning (a deliberate skip is a healthy state — the real success ping lives at the very end of `run_once()`, unreachable on an early return, so without this every skip would eventually false-alarm "pipeline down"). Accepted tradeoff of the 5h window: content can go up to ~11h without a fresh pull if a manual trigger lands right before a scheduled slot.

## Dwell auto-read timer raised 20s → 120s (3 September 2026)
Ash reported stories disappearing from the feed while he was still reading them. Root cause is a four-step chain, not a single bug: `useDwellVisibility` (threshold 0.5) fires `onDwellEnd` as soon as a card drops below half-visible → `endDwell` (`ReaderClient.tsx`) auto-marks it read if it was on screen past the dwell threshold → `markRead` updates `readIds` optimistically, before the network round-trip → `visibleSolos` filters `readIds` out of the feed, and `showUnreadOnly` defaults to **true**. Net effect: read a card for longer than the threshold, scroll down slightly to continue it, and the card is unmounted under you while everything below jumps up. On the Today tab the card isn't removed but is re-sorted to the bottom by `rankItems` (`ranking.ts`), which looks the same from the reader's seat.

**Changed:** the threshold only, 20 → 120 seconds (`ReaderClient.tsx`, the sole place it's defined). `npm run build` clean; confirmed `a>120` in the emitted chunk.

**Root cause fixed 14 September 2026** (Ash asked for it after the timer alone didn't stop cards vanishing mid-read): dwell-triggered reads go into `heldIds` in `ReaderClient.tsx`. A held card still counts as read (greys out, unread count drops) but is excluded from `layoutReadIds`, the read set used by `visibleSolos`, `mergedFeed` and `TodayFeed`/`rankItems` for filtering and sorting — so it stays put. Held ids are cleared at the top of `loadContent` (tab switch, pull-to-refresh, pipeline trigger) and when the Unread/All toggle is flipped. An explicit "mark read" tap is not held and removes the card immediately. Threshold stays 120 s. Deployed to Netlify same day (`npm run build` clean, `hold:!0` confirmed in chunk).

**Unconfirmed, worth checking if this resurfaces:** with `threshold: 0.5`, a card taller than ~2× the viewport can never reach a 0.5 intersection ratio, so no threshold crossing ever fires and `onDwellStart` may never run for it — meaning the longest stories might never auto-mark-read at all. Reasoned from the IntersectionObserver spec, not observed in the running app.

**How it works** (`pipeline/storylines.py`)
- **Assignment** happens in `cluster.embed_and_cluster_story` (right after the embedding is stored): the single choke point of all five embed paths, so each story is assigned exactly once. News categories only. Shortlist = same category, last 7 days, cosine ≥ 0.70, best 8 → one Flash call (thinking 0, temp 0) picks the candidate that is the same *specific event*, or null. A storyline candidate = join; a lone earlier report = a new storyline holding both. Candidates from one storyline collapse into one entry.
- **Round-up guard (9 Oct):** a story whose `short.lead` starts "Round-up" (the session 1 round-up prompt) never joins a storyline, is never a candidate and costs no Gemini call (`is_round_up`). 23 of 141 news stories in the last week were round-ups, and this removes the S24 wrong merge. Stories without `short` aren't recognised; the prompt still says null for round-ups.
- **Recaps**: `run_once` step 7 (`refresh_recaps_live`). Targets = storylines with `story_count ≥ 3`, last report within 7 days, and `recap_story_count != story_count`. `make_recap` makes one call and **at most one re-ask**; `build_recap` is the validator (below). Dates are Europe/London days.
- **Two backends, one engine**: `DbBackend` (live; shortlist via the `match_recent_stories` RPC, asked for 2× the cut because round-ups are filtered afterwards) and `MemoryBackend` (backfill/tests; filters round-ups before the cut). The RPC avoids pulling ~10 MB of embeddings per cron run.
- **Fail-soft** (verified against the real DB): a missing table/column/RPC switches storylines off for the process with one hint line; 3 Gemini failures in a row switch them off for the run; every hook catches everything. A story is never lost or delayed by a storyline.
- Gemini calls all go through `llm.flash_json`, so they appear in `pipeline_runs` totals (read after step 7).

**Recap validation (`build_recap`), session 2**
